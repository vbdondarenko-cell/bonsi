# BONSI Mail

Стан: код готовий і перевірений автоматично (юніт-тести, реальна SMTP-розмова з локальним сервером, аудит подій); **реальну доставку на живу скриньку НЕ підтверджено** —
для цього потрібні поштова скринька хостингу (або домен + Resend) і тест із реальною адресою (чекліст нижче). Доки тест не пройдено, доставку вважати **не робочою**.
Реальні листи не відправляються, доки власник не задасть `EMAIL_PROVIDER` та облікові дані.

## Провайдери (`EMAIL_PROVIDER`)

| Значення | Коли | Змінні |
| --- | --- | --- |
| `smtp` | **пошта хостингу** (скринька на домені BONSI): без сторонніх сервісів і платних тарифів | `SMTP_HOST`, `SMTP_PORT` (465), `SMTP_SECURE` (`true` для 465; `false` → STARTTLS на 587), `SMTP_USER`, `SMTP_PASS` |
| `resend` | якщо домен налаштовано в Resend | `RESEND_API_KEY` |
| `mock` | лише розробка (у production заборонений) | — |
| *(порожньо)* | листи лишаються в черзі `email_outbox`, нічого не вдаючи «відправленим» | — |

Спільні: `EMAIL_FROM` (`BONSI <no-reply@домен>` — адреса ТІЄЇ ж скриньки/домену, інакше SPF/DMARC відхилять), `EMAIL_REPLY_TO`, `NEXT_PUBLIC_SITE_URL`, `CRON_SECRET` (≥ 24 символи),
`SEND_EMAIL_HOOK_SECRET` (для кодів входу). Перевірка конфігурації: `npm run check:env` (у production неповна пошта — помилка або попередження).

### Налаштування пошти хостингу (потрібно від власника)
1. У панелі хостингу (cPanel/ISPmanager тощо) створити скриньку `no-reply@<домен>` і ще одну для відповідей студії (`studio@<домен>`); записати пароль у менеджер паролів.
2. З розділу «Налаштування клієнта пошти» взяти **хост вихідної пошти** (часто `mail.<домен>`), порт і тип шифрування. Використовуйте 465/SSL або 587/STARTTLS; порт 25 не використовувати.
3. Прописати змінні на сервері застосунку (не в репозиторії!): `EMAIL_PROVIDER=smtp`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER=no-reply@<домен>`, `SMTP_PASS`, `EMAIL_FROM`, `EMAIL_REPLY_TO`.
4. DNS домену: SPF (`v=spf1 +a +mx include:<spf хостингу> ~all` — точне значення дає хостинг), DKIM (увімкнути в панелі хостингу й додати TXT), DMARC (`_dmarc TXT "v=DMARC1; p=none; rua=mailto:dmarc@<домен>"`, згодом `quarantine`).
5. Перевірити з реальної скриньки (Gmail/Outlook): лист у Inbox (не Spam), заголовки `SPF=pass`, `DKIM=pass`, `DMARC=pass` («Показати оригінал»).
6. Cron: щохвилини `curl -fsS -X POST -H "Authorization: Bearer $CRON_SECRET" https://<сайт>/api/internal/emails` (cron хостингу або зовнішній безкоштовний планувальник).

**Обмеження SMTP.** Немає серверної ідемпотентності (на відміну від Resend): якщо сервер прийняв лист, а процес упав до відмітки «надіслано», можливий дубль.
Зменшує: детермінований `Message-ID` з ключа ідемпотентності та заголовок `X-BONSI-Idempotency-Key`. Ліміти листів на добу/годину задає хостинг — з'ясуйте їх (нова пошта хостингу часто 100–500 листів/год).

## Класифікація збоїв (однакова для провайдерів)
- Тимчасові (повтор 1/2/4/8/16 хв, до 6 спроб, строк життя 7 діб): мережа, таймаут, SMTP 4xx, SMTP 535 (невірний пароль — лист не втрачається, поки не виправлять пароль), Resend 5xx і **429**.
- Постійні (одразу `failed`): SMTP 550–554 (скриньки немає/відмова змісту), Resend 4xx крім 429. До помилки в БД пишеться лише код (`smtp_550`, `resend_429`), без адреси й тексту провайдера.

## Два шляхи листів
1. **Листи подій** (заявка прийнята, нове повідомлення, пропозиція, рішення, рахунок, оплата, завершення) → таблиця `email_outbox` (ідемпотентні ключі, повтори 1/2/4/8/16 хв, межа 6 спроб, строк життя 7 діб, зміст не зберігається — лише змінні шаблону) → диспетчер `POST /api/internal/emails` (Bearer `CRON_SECRET`, cron щохвилини) → провайдер (`EMAIL_PROVIDER=resend`). Збій провайдера не губить лист: він лишається в черзі. Заявка завжди ставиться в чергу (без залежності від провайдера); пропущені донаповнює `email_backfill_order_received()` у кожному запуску диспетчера.
2. **Коди входу клієнта** — це листи Supabase Auth, а не наша черга (код — секрет, його не можна зберігати). Провайдер з пункту 1 ними **не керує**. Два способи:

### A. Custom SMTP у Supabase (простіше)
Supabase Dashboard → Authentication → SMTP Settings: хост, порт, логін і пароль **тієї ж скриньки хостингу** (для Resend: `smtp.resend.com`, порт `465`, user `resend`, пароль = API-ключ), відправник `BONSI <no-reply@<домен>>`. Шаблони Authentication → Emails («Magic link», «Confirm signup») мають містити `{{ .Token }}` і `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email` (еталон — `supabase/templates/*.html`). Ліміт листів: Authentication → Rate Limits.

### B. Send Email Hook (повний контроль, своя адреса й шаблон)
Маршрут `POST /api/auth/email-hook` перевіряє підпис Standard Webhooks (`SEND_EMAIL_HOOK_SECRET`, допуск часу 5 хв), приймає лише `magiclink|signup|email`, надсилає код + посилання через наш провайдер (`EMAIL_PROVIDER`: smtp або resend), повертає 502/503 у форматі Supabase при збої (вхід тоді чесно показує «тимчасово недоступний»). Налаштування: Dashboard → Authentication → Hooks → Send Email → HTTPS → `https://<сайт>/api/auth/email-hook`, згенерувати секрет, прописати його як `SEND_EMAIL_HOOK_SECRET` на хостингу, додати `EMAIL_PROVIDER` з відповідними змінними (SMTP_* або `RESEND_API_KEY`), `EMAIL_FROM`, `NEXT_PUBLIC_SITE_URL`.

Адреси адміністраторів: `/login` не надсилає їм код і відповідає так само, як для клієнта (існування акаунта не розкривається).

## DNS домену відправника
SPF `v=spf1 include:<провайдер> ~all`; DKIM — ключі провайдера; DMARC `_dmarc TXT "v=DMARC1; p=none; rua=mailto:dmarc@<домен>"` → після спостереження `quarantine`. From: `BONSI <no-reply@<домен>>`, Reply-To — адреса студії.

## Чекліст «доставка працює» (поки НЕ пройдено)
- [ ] SPF, DKIM, DMARC налаштовано; у заголовках реального листа `spf=pass dkim=pass dmarc=pass`.
- [ ] Обрано A або B і налаштовано в Supabase Dashboard.
- [ ] Реальна заявка з живої скриньки → лист «Заявку отримано» у Inbox (не Spam), `email_outbox.status = sent`.
- [ ] Вхід: код приходить у Inbox, вводиться, вхід успішний; повторне надсилання, прострочений і використаний код відхиляються.
- [ ] Імітація збою (невірний ключ провайдера): вхід показує «недоступний», заявки лишаються в черзі й доходять після виправлення.
- [ ] Адмінпанель → Налаштування → «Пошта BONSI»: черга порожня, помилок немає.

## Автоматичні перевірки (CI)
`src/lib/email/*.test.ts`: шаблони й екранування HTML; відправка черги; **реальна SMTP-розмова** (автентифікація, `From/Reply-To/Message-ID`, захист від ін'єкції в тему, 550 → постійна, 451/535/недоступність → тимчасова); 429 повторюється; ключі ідемпотентності детерміновані (статичний аудит усіх місць, що ставлять листи в чергу); шаблони в коді = обмеження БД; у журналах пошти немає токенів/паролів; підпис хука (`route.test.ts`).

## Події → шаблони
`order_received` (заявка), `new_message` (повідомлення студії, ≤1 на 15 хв на проєкт), `new_proposal`, `proposal_decision` і `deliverable_decision` (підтвердження клієнту), `invoice_issued`, `payment_confirmed` (лише після підтвердження в журналі), `project_completed`. `cabinet_invite` і `login_code` у черзі не використовуються (запрошення й коди відправляє Supabase Auth). Порожні/демонстраційні листи не створюються: немає адресата — немає запису.
