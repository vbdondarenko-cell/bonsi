## Застосунок

| Область | Перевірка |
| --- | --- |
| `/admin` ↔ `/app` | окремі входи й guard'и; адмін у `/app` отримує 404; клієнт у `/admin` — редирект на вхід (E2E) |
| CSRF | серверні дії Next.js перевіряють `Origin`; API-маршрути з секретами — Bearer (`CRON_SECRET`, підпис хука) з `timingSafeEqual` |
| IDOR | усі читання через RLS-клієнт користувача; `service_role` лише на сервері для черги листів/заявок; перевірка власності на PDF-маршрутах |
| Секрети | тест `secrets.test.ts` шукає JWT/`sb_secret_`/приватні ключі в коді; `check:env` забороняє секрети в `NEXT_PUBLIC_*`; пароль SMTP і ключ Resend лише з env |
| Повторні дії | `run_operation` (fail-closed), детерміновані ключі листів, ідемпотентні RPC платежів (`docs/STABILITY.md`) |
| Файли | приватне сховище, перевірка типу/розміру, видалений файл → 404 (E2E) |
| PDF | лише заморожена версія для клієнта; перед друком перевіряється SHA-256 (підміна → 409); `no-store`, `nosniff` |

## Відомі обмеження

- Немає незалежного пентесту, DAST і перевірки залежностей у CI (`npm audit` не є частиною релізного шляху).
- Захист від зламаних паролів у Supabase Auth вимкнено (дія власника, `docs/MIGRATION_PLAN.md` §9).
- Підтвердження рішень у кабінеті — не КЕП (прямо написано в документах і PDF).
- SMTP не має серверної ідемпотентності: можливий дубль листа, якщо сервер прийняв лист, а процес упав до відмітки «надіслано» (`docs/MAIL.md`).
