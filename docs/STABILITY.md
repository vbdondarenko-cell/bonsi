# Стабільність форм адмінпанелі та E2E (V0.5)

## Зависання кнопки «Надсилаємо…» — першопричина

**Симптом.** Серверна дія виконувалась і записувала дані, HTTP-відповідь приходила повністю (у трейсах: 200, 16–25 КБ за ~60 мс),
але форма лишалась у стані pending: кнопка «Надсилаємо…» / «…» неактивна, результат не показаний. Траплялось у різних формах
(створення завдання, кошторису, відправка передачі, відповідь у підтримці) і частіше у WebKit та Firefox.

**Причина (доведена).** Маршрутний `src/app/admin/(panel)/loading.tsx` (Suspense-межа сегмента) разом із серверною дією, що викликає
`revalidatePath`: у Next 15.5.28 клієнтський перехід, який застосовує перерендерену сторінку з відповіді дії, інколи не завершується,
і `useActionState` лишається pending.

**Доказ.** Мінімальний застосунок (Next 15.5.28, React 19.3.1, без Supabase) із формою `useActionState`, дією з `revalidatePath`
і `loading.tsx` у сегменті, 30–40 відправок за прогін:

| Конфігурація | WebKit | Firefox |
| --- | --- | --- |
| з `loading.tsx` | 11/60, 4/30, 4/30, 1/30, 10/40, 6/40 зависань | 5/60 |
| без `loading.tsx` | 0/110 | 0/30 |
| без `loading.tsx`, Chromium | 0/30 | — |

(Рядок Chromium — окремий замір: у ньому WebKit і Firefox не вимірювались.)

Скидання форми (`useLayoutEffect`), блокування кнопки до гідрації та `router.refresh()` на частоту зависань не впливали
(зависання лишалися й без них). Тому `loading.tsx` видалено з адмінського сегмента; сторінки `force-dynamic`, скелетон не потрібен.

**Той самий механізм у публічній частині.** `src/app/(site)/portfolio/loading.tsx` змушував Next віддавати HTTP 200 для неіснуючого
кейсу (`notFound()` спрацьовував після початку стрімінгу) — «м'який 404». Файл видалено; E2E перевіряє 404 до публікації й після зняття.

**Правило.** Не додавати `loading.tsx` у сегменти, де є форми з серверними діями та `revalidatePath`. Для довгих запитів
використовувати локальний `<Suspense>` усередині сторінки поза формою.

## Захист від повторного виконання (fail-closed, атомарно)

**Архітектура.** Усі неідемпотентні дії (35 адмінських і 11 клієнтських RPC, закритий білий список у SQL) виконуються через
`public.run_operation(p_op, p_fn, p_args)` (міграція `20261110_operations`). Захоплення ідентифікатора спроби, бізнес-функція й
збереження результату — **в одній транзакції PostgreSQL**. TypeScript-обгортка: `rpcOnce()` у `src/lib/operations.ts`.

| Ситуація | Що відбувається |
| --- | --- |
| Нова операція | виконується, результат зберігається, `replayed = false` |
| Подвійний клік, повтор після таймауту/перезапуску, паралельний дубль | другий запит чекає на перший (блокування ключа), далі отримує **збережений** результат, `replayed = true`, бізнес-функція вдруге не викликається |
| Помилка бізнес-функції | відкочується все, включно із записом операції: нічого не збережено, повтор з тим самим ID безпечний |
| Той самий ID для іншої функції / інших аргументів / іншого користувача | `operation_conflict`, чужий результат не віддається |
| Збій між «захопити» і «записати» | неможливий: це одна транзакція; «pending» у БД не існує за побудовою |
| Відповідь загубилась (клієнт отримав timeout) | клієнт зберігає той самий ID (`OPERATION_RETRY_TEXT`) і повторює; сервер віддає збережений результат |
| Пізній повтор | записи не видаляються автоматично |

**Fail-closed.** Якщо ідентифікатора немає, він некоректний, міграція не застосована (`PGRST202`/`42883`), Supabase недоступний або
відповідь незрозуміла — бізнес-функція **не викликається** і користувач бачить помилку, а не «успіх». Це перевірено тестами
(`src/lib/operations.test.ts`, `src/lib/workspace/operations.db.test.ts`).

**Клієнт.** `useGuardedAction` (`src/lib/forms/use-guarded-action.ts`): один UUID на спробу (`_op`), повторна відправка тієї ж спроби
ігнорується (додатковий рівень), після помилки введене повертається у форму, кнопка неактивна до гідрації. Ідентифікатор міняється
лише після остаточної відповіді сервера. Чат клієнта (`message-thread.tsx`) робить те саме вручну.

**Порядок розгортання.** Застосунок V0.5 *вимагає* міграцію `20261110`: без неї дії зі списку показують помилку й не виконуються
(безпечна відмова). Тому міграції застосовуються ДО розгортання застосунку (див. `docs/MIGRATION_PLAN.md`).

- Лист про передачу має детермінований ключ із `handover_records.submitted_at`.
- Гроші: унікальність `(proposal_id, schedule_index)` для рахунків, `not_pending` для повторного підтвердження оплати, межа повернення
  `refund_exceeds_paid`, ідемпотентність подій провайдера за `event_id`.

## Ізоляція E2E

- Фінансовий тест міряє дельти від власного baseline, а не абсолютні значення глобальної статистики.
- `retries: 0` у всіх конфігураціях Playwright; CI додатково повторює `ops.spec.ts` 3 рази та сценарії клієнта 1–13 2 рази.
